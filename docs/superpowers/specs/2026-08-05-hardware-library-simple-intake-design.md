# 简化硬件资料库设计

日期：2026-08-05  
状态：TZ 已确认执行  
范围：Agent10 Asset Library 与 `/agent10` Web 路由；不改变共享 Web 外壳。

## 目标

资料库首先回答两个问题：**我有什么硬件？各有多少？**

TZ 不应被要求理解 `hardware_model`、`hardware_unit`、`assembly_layout`、证据等级或 JSON。系统以照片、一个 HTTPS 链接和一条可选说明生成候选资料，TZ 只在最终页面确认必要信息。Obsidian 保存完整长期资料，SQLite 提供查询投影；Codex 和其他 Agent 使用同一份经过来源标记的记录做软件设计与布局建议。

## 用户可见的信息架构

`/agent10` 保留共享的“上下分区”壳，内部切换为两个子页面，不新增全局路由：

- **我的硬件**（默认，只读）：顶部显示“硬件种类、可用件数、待确认、需补资料”四个数字；下方提供搜索和系统自动分类筛选。卡片只显示照片缩略图、名称、品牌/型号（如已知）、可用/总数量和简明状态。
- **录入 / 编辑**：由“录入硬件”或卡片的“补货 / 编辑”进入。页面没有 JSON、模型/单元/布局选择器，也没有要求输入厂商、版本或发布日期。

详情页可显示给 TZ 的内容为“用于什么、已知接口/供电/尺寸、资料、需要补什么”；技术溯源、原始资料正文、私有照片路径、令牌、序列号、MAC 和 Wi-Fi 信息永不进入 Web 投影。

## 最小录入流程

1. TZ 可上传一至多张照片，粘贴一个可选 HTTPS 链接，并写一条可选说明（例如“新买两个，给水位传感器用”）。
2. 点击“识别并生成建议”。服务器保存私有草稿附件，受控抓取该链接，并运行已批准的候选分析；页面显示明确的进行中、完成、不可用或需补拍状态。
3. 系统显示一张建议卡：`名称`、`数量`、`新增或合并到现有库存`、一张主图、关键规格和有冲突/不确定时才出现的提示。名称或数量无法可靠得到时，才要求 TZ 补这一项。
4. TZ 可修改建议，选择新增或合并，然后点击“确认入库”。服务端建立不可变快照并完成 Agent10 现有的显式验收/发布链；Obsidian 写入成功且 SQLite 镜像同步后才显示“已入库”。
5. 现有硬件的补货、改名或补资料复用相同草稿与确认界面。历史快照保留；不得在浏览页面静默覆盖已接受事实。

刷新页面不恢复未确认的编辑草稿。已创建的服务器草稿可在同一受控会话中继续读取，但浏览器不保存原始内容、令牌或伪造的“已确认”状态。

## 隐藏的领域模型

现有三类受治理记录继续存在，但不再作为用户填写的分类：

- `hardware_model`：系统维护的型号/资料档案，承载官方能力、接口、供电、标称尺寸和官方/第三方参考。
- `hardware_unit`：一个库存批次，承载数量、可用状态与可选实测。库存总数是同一型号所有批次的聚合；新增数量创建可追溯批次，不直接篡改旧批次事实。
- `assembly_layout`：仅在 Codex 或项目装配工作流确有装配目标时创建；不出现在普通入库流程。

Web 新增的 `inventory_summary` 是脱敏只读投影，不是第四个事实源。它按型号聚合数量、主图和用户可见状态；现有 24 条记录先通过投影兼容，不进行破坏性迁移。

系统自动分类仅用于浏览筛选，使用：开发板、传感器、执行器、电源、结构件、连接件、其他。分类不确定时为“其他”，不阻塞入库。

## 资料、照片与事实边界

### 单链接资料

输入框只接受一个 `https://` URL。点击“获取并比对”才会抓取，绝不自动爬取、登录、携带 Cookie/令牌或跟随到私有网络。抓取器须逐跳校验 HTTPS、域名解析结果和重定向目标，拒绝 localhost、环回、私有/保留地址、嵌入凭据 URL、非允许内容类型、超限响应和下载文件。它保存规范 URL、抓取时间、内容哈希、可得标题和受限文本摘要；原始正文不向浏览器公开。

链接即使没有可用硬件字段，也作为关联的官方软件/开发资料保留。它可提供 SDK、协议、引脚语义、固件 API 或开发限制；“资料已保存，未形成硬件候选”是有效结果，不视为失败。

### 照片与尺寸

上传只接受限定图片格式和大小，计算哈希并清除 EXIF 后保存到 Agent10 私有草稿附件区。展示给 Web 的只有经批准的缩略图或摘要。照片内明确标注的尺寸可形成 `label_or_photo` 候选；它永远不自动升级为 `measured`。孔位、弯折半径、热间距、净空和未在来源中明确给出的数据保持空值，并显示“需补拍/实测”而不是猜测。

### 候选分析

分析器只能生成候选：名称/型号、数量、资料字段、尺寸标注、可能的重复项和字段冲突。确定性规则负责 URL 校验、附件校验、去重键、快照、权限、持久化和发布；模型结果没有事实或写入权。

字段比较按来源显示为“一致、冲突、待确认、无候选”。官方资料可支持型号标称能力；照片标注可支持可见标签或标注；实测仍需带工具、方法和时间；TZ 的手工修改可成为待验收候选，但不伪称实测。

## 模型与外部访问治理

本次批准的用户体验允许在用户点击后使用受控网页抓取和候选分析，但当前全局模型路由记录没有 Agent10 图片/文档分析路线。实现分两层：

1. 无模型也可用：上传、链接保存、确定性安全校验、草稿、人工输入、重复项建议和显式验收全部正常工作。
2. 模型分析仅在 `GLOBAL_MODEL_ROUTING_RECORD.md` 已登记 `Agent10 / hardware_reference_analysis` 后启用。该路线必须写明提供商、解析模型、运行/推理位置、允许的数据类别、最大输入、候选输出契约、执行审计、不可用状态和 `fail_closed` 行为。

路线未登记、凭据不可用或调用失败时，页面明确显示“自动分析暂不可用；资料已保存，可手动确认”，不得调用其他提供商或将模型输出伪装为结果。首次实际外部调用前，界面与运行审计记录提供商、用途，以及发送的是受限图片、受限网页正文还是两者。

## API 与确认契约

保留现有硬件 GET、最终 `accept` 和服务端令牌代理。新增的所有 mutation 均须显式允许、以 Agent10 服务端处理：

- `GET /api/agent10/hardware/summary`：库存聚合投影。
- `POST /api/agent10/hardware/drafts`：创建空白或编辑草稿；返回草稿 ID 和不可伪造的版本标识。
- `POST /api/agent10/hardware/drafts/:id/attachments`：多段上传私有图片；不返回本地路径。
- `POST /api/agent10/hardware/drafts/:id/reference`：保存并受控抓取单个 HTTPS URL。
- `POST /api/agent10/hardware/drafts/:id/analyze`：启动确定性/已批准模型分析作业。
- `GET /api/agent10/hardware/analysis-jobs/:id`：返回脱敏状态、候选和冲突摘要。
- `PATCH /api/agent10/hardware/drafts/:id`：保存 TZ 可编辑字段及合并意图，使用草稿版本防止覆盖。
- `POST /api/agent10/hardware/drafts/:id/prepare`：将界面草稿编译为一组受校验硬件记录和不可变确认包快照。
- `POST /api/agent10/hardware/drafts/:id/accept`：仅接受刚生成的确认包哈希；它在后台协调该包内的既有 intake 发布，任一条局部失败即返回部分失败。
- 既有 `POST /api/agent10/hardware/intakes/:id/accept`：仅接受刚生成的快照哈希。

浏览器不得提交或自行声称 `accepted_by: "TZ"`。Web 代理在服务端从受控的本地操作身份获得验收人；在身份机制未配置时，最终按钮必须禁用并说明原因。一个新增条目的型号资料和库存批次作为一个确认包被用户确认一次，但仍按现有单记录写入合同处理并将局部故障明确记录。

## 可靠性与验收

- 所有草稿、附件、抓取结果和分析作业都有操作键/内容哈希，重复请求复用结果，不重复写入。
- 任何 Obsidian 或 SQLite 局部失败仍由既有 gap journal 和原子写合同处理；不得显示“已入库”。
- 公开投影始终脱敏，且不包含附件字节、原始正文、绝对路径、源引用内部地址或敏感设备身份。
- 现有硬件记录、查询、关系和已发布 Obsidian 页面必须保持可读。
- 定向测试覆盖：URL/SSRF 与附件校验、候选不升级事实、去重与数量聚合、草稿版本冲突、重复作业幂等、验收快照漂移、发布局部失败、Web allowlist/令牌边界，以及桌面和窄屏的两子页面。

## 非目标

不做自动采购、价格、供应商 CRM、网页批量爬取、外网设备控制、浏览器直写 Obsidian、公开图片库、自动把物理候选当成实测、或把硬件资料库变成完整 Obsidian 编辑器。
